# ThreeQStudyMachine HarmonyOS 全面升级总方案

## 1. 升级目标

本方案面向 `ThreeQStudyMachine_HarmonyOS` 项目，目标是把现有学习机应用升级为符合鸿蒙生态、具备 Google 风格视觉语言、可自动化验证和可持续运维的产品级项目。

核心目标：

1. UI 采用 Google Material Design 3 的清晰、轻量、卡片化、强状态反馈风格，但实现层必须基于 HarmonyOS ArkUI 原生组件。
2. 代码遵循 ArkTS、ArkUI、Stage 模型、模块化工程、资源管理和安全合规规范。
3. 功能形成学习闭环：学习任务、课程、练习、测评、错题、复习、学习报告、家长/教师管理。
4. 自动化覆盖研发、构建、测试、发布、日志、监控、回滚。
5. 用户操作手册、运维手册、开发规范、验收清单完整交付。
6. 项目上传 GitHub，通过 Issue、PR、优化日志评论间接沟通和跟踪进度。

## 2. 技术边界

### 2.1 必须遵守

1. 不直接引入 Android Material 组件库，不复制 Android 原生实现。
2. UI 使用 ArkUI 声明式范式实现。
3. 页面导航优先使用 HarmonyOS 当前推荐的 `Navigation`、`NavDestination`、`NavPathStack` 等体系。
4. 状态管理使用 ArkUI 原生装饰器和应用级存储机制，根据场景区分组件状态、页面状态、应用状态、持久状态。
5. 工程构建使用 DevEco Studio、Hvigor、HarmonyOS SDK 体系。
6. 所有设备能力调用必须经过权限声明、运行时授权、失败兜底和隐私说明。
7. 用户数据、儿童数据、学习记录、账号 token、设备绑定信息不得明文散落存储。

## 3. Google 风格 UI 设计方案

### 3.1 视觉原则

采用 Material Design 3 的视觉气质：

1. 大面积浅色背景，信息层级清楚。
2. 主操作使用稳定蓝色，辅助状态使用绿色、黄色、红色。
3. 卡片用于承载具体学习任务、课程、报告条目，不把整个页面做成卡片堆叠。
4. 圆角控制在 8 到 12，儿童入口按钮可适当放大。
5. 阴影轻、边界清楚、动效克制。
6. 图标统一线性风格，避免混用多套风格。
7. 首页强调任务驱动，而不是功能菜单堆砌。

### 3.2 设计 Token

必须建立统一 token 文件或主题模块：

颜色：

- `colorPrimary`: 主蓝色，用于主要按钮、选中态、关键进度。
- `colorSuccess`: 学习完成、掌握、同步成功。
- `colorWarning`: 需要复习、弱项提醒、剩余时间。
- `colorError`: 提交失败、离线异常、权限缺失。
- `colorSurface`: 页面背景、卡片背景。
- `colorOutline`: 分割线、输入框边界。
- `colorTextPrimary`
- `colorTextSecondary`
- `colorTextTertiary`

尺寸：

- `space4`
- `space8`
- `space12`
- `space16`
- `space24`
- `space32`
- `radius8`
- `radius12`
- `radius16`
- `touchTargetMin`: 不低于 44vp，儿童核心操作建议不低于 48vp。

字体：

- 页面标题
- 分区标题
- 卡片标题
- 正文
- 辅助说明
- 数字型进度

3. 练习与测验

   - 答题卡
   - 计时器
   - 草稿/标记
   - 提交前确认

4. 错题本

   - 错因标签
   - 复习计划
   - 再练一次

5. 学习报告
   - 今日、周、月维度
   - 学习时长
   - 正确率
   - 知识点掌握
   - 进步趋势
   - 给家长/教师的建议

6. 家长/教师管理
   - 学生列表
   - 任务下发
   - 内容限制
   - 学习报告
   - 设备绑定
   - 远程配置

7. 设置中心
   - 账号与设备
   - 缓存管理
   - 离线资源
   - 隐私权限
   - 版本更新
   - 帮助与反馈

### 3.4 必须补齐的页面状态

每个主要页面必须有：

1. 首次加载状态。
2. 空数据状态。
3. 网络错误状态。
4. 无权限状态。
5. 离线状态。
6. 同步中状态。
7. 操作成功状态。
8. 操作失败重试状态。

## 4. 功能升级方案

### 4.1 学生端

1. 账号登录、设备绑定、学生档案。
2. 今日任务自动生成。
3. 课程学习、章节进度、继续学习。
4. 练习、测验、错题记录。
5. 错题复习和知识点回补。
6. 学习报告。
7. 离线学习和联网同步。
8. 语音朗读、护眼模式、学习时长提醒。
9. 帮助中心和问题反馈。

### 4.2 家长端

1. 绑定学生和设备。
2. 查看学习报告。
3. 设置学习计划。
4. 查看错题和薄弱点。
5. 设置内容限制、使用时长、休息提醒。
6. 接收学习完成和异常通知。

### 4.3 教师/管理员端

1. 班级、学生、课程、题库管理。
2. 任务下发。
3. 学情统计。
4. 内容审核。
5. 版本与资源包发布。
6. 设备管理。

### 4.4 推荐与智能化

第一阶段使用规则引擎：

- 错误次数高的知识点优先复习。
- 正确率低于阈值的章节进入强化练习。
- 长时间未复习的知识点进入间隔复习。
- 连续高正确率的知识点降低推送频次。

第二阶段再接入 AI 能力：

- 个性化练习推荐。
- 错因分析。
- 学习建议生成。
- 题目讲解生成。
- 语音问答。

### 5.2 分层职责

UI 层：

- 只负责页面、组件、交互状态。
- 不直接拼接口参数。
- 不直接操作数据库。

Domain 层：

- 封装学习任务、答题、错题、报告、同步等业务规则。
- 负责核心业务模型。

Data 层：

- 网络接口。
- 本地缓存。
- 离线队列。
- DTO 与领域模型转换。

Infra 层：

- 日志。
- 埋点。
- 错误码。
- 配置。
- 权限。
- 加密。
- 设备能力。

### 5.3 数据同步

必须设计离线优先流程：

1. 用户操作先落本地。
2. 生成同步任务。
3. 后台或下一次联网时同步。
4. 同步失败保留重试。
5. 服务端冲突返回明确状态。
6. 客户端展示同步结果。

冲突策略：

- 学习进度取最大完成度。
- 答题记录按提交时间保留完整记录。
- 错题状态以最新用户操作为准。
- 家长/教师配置以服务端最新版本为准。

## 6. HarmonyOS 代码规范

详细规范见 `docs/02_HARMONYOS_CODE_STANDARDS.md`。

总原则：

1. ArkTS 类型必须明确，禁止随意使用 `any`。
2. 页面组件不超过合理长度，复杂页面拆分为区域组件。
3. 公共组件必须无业务副作用。
4. 网络、存储、权限、日志必须统一封装。
5. 路由参数必须类型化。
6. 资源使用 `resources` 和主题 token 管理，禁止大量硬编码颜色和字号。
7. 异常必须进入统一错误模型。
8. 敏感信息不得写入普通日志。

## 7. 自动化与运维

### 7.1 GitHub 分支策略

推荐：

- `main`: 稳定发布分支，必须保护。
- `develop`: 集成分支。
- `feature/*`: 功能分支。
- `fix/*`: 缺陷修复。
- `docs/*`: 文档。
- `release/*`: 发布准备。

如果希望和 Codex 工作流统一，也可以使用 `codex/*` 作为自动化改造分支前缀。

### 7.2 GitHub Actions

必须建立以下流水线：

1. Pull Request 检查
   - 代码格式检查。
   - ArkTS 静态检查。
   - 单元测试。
   - 构建检查。
   - 文档链接检查。

2. 主分支构建
   - 生成 HAP 或 APP 产物。
   - 上传构建产物。
   - 生成版本信息。

3. 发布流水线
   - 版本号校验。
   - 签名配置检查。
   - 构建 release 包。
   - 生成 changelog。
   - 灰度发布或人工确认发布。

注意：HarmonyOS 构建通常依赖 DevEco Studio、HarmonyOS SDK、签名配置。GitHub 托管 runner 不一定具备完整环境，正式构建建议使用自托管 runner。签名证书、密钥、账号 token 必须放入 GitHub Secrets 或内部密钥系统，不能提交到仓库。

### 7.3 自动化测试

最小测试矩阵：

1. 单元测试
   - 学习任务生成。
   - 答题判分。
   - 错题规则。
   - 同步冲突。
   - 推荐规则。

2. UI 自动化
   - 登录。
   - 首页加载。
   - 课程学习。
   - 练习提交。
   - 错题复习。
   - 学习报告查看。
   - 设置缓存清理。

3. 接口测试
   - 鉴权。
   - 课程列表。
   - 题目拉取。
   - 答题提交。
   - 报告生成。
   - 同步队列。

4. 兼容性测试
   - 不同屏幕尺寸。
   - 横竖屏策略。
   - 弱网。
   - 断网。
   - 冷启动。
   - 后台恢复。

### 7.4 监控指标

产品指标：

- 日活。
- 完成今日任务人数。
- 课程完成率。
- 练习提交成功率。
- 错题复习完成率。
- 家长报告打开率。

技术指标：

- 崩溃率。
- 冷启动耗时。
- 页面加载耗时。
- 接口失败率。
- 同步失败率。
- 离线队列积压数。
- 包体积。

### 7.5 回滚机制

必须支持：

1. 配置回滚。
2. 课程资源回滚。
3. 题库版本回滚。
4. 客户端版本回滚策略。
5. 灰度人群撤回。
6. 服务端接口兼容旧版本。

## 9. OpenClaw 执行方式

OpenClaw 执行细则见 `docs/01_OPENCLAW_EXECUTION_PROTOCOL.md`。

执行原则：

1. 每个升级点必须对应 GitHub Issue。
2. 每个 Issue 必须有验收标准。
3. 每次提交 PR 前必须写优化日志。
4. 每个 PR 必须说明改动范围、截图、验证结果、风险。

- 主题 token。
- 公共组件库。

- 练习页新版。
- 错题本新版。
- 报告页新版。
- 设置页新版。

验收标准：

- UI 风格统一。

### 阶段 3：业务闭环

交付物：

- 学习任务。

- 练习提交。
- 错题归因。

- 学习报告。
